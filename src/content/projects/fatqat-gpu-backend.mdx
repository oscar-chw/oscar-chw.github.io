## The problem

<Term t="state vector">A state-vector quantum simulator</Term> keeps every amplitude of the quantum state in memory and updates all of them for every gate. The state doubles with each added qubit, so larger circuits are limited by how fast the machine can move memory. FatQat, an open-source simulator by spaceqat, runs on the CPU. I wanted a GPU engine that existing FatQat code could use without changes and without losing accuracy.

## What I built

- **CUDA (GPU) execution for all four simulation methods** behind the simulator's existing interfaces, so a circuit runs unchanged on either engine.
- **Double precision throughout**, matching the CPU engine rather than trading accuracy for speed.
- **Exact shot branching**: shots that share a history are simulated once and split only where they differ, with identical counts.
- **Exact circuit simplification**, and randomized differential checks that compare every "same result" claim against the reference.
- **An Apple-GPU runtime** (`runtime="metal"`) that computes binary64 in software, bit-identical to the CPU engine, and `runtime="auto"`, which picks the faster runtime for each run.
- A fork kept in sync with upstream FatQat, inspired by the course CENG5280, and **a fix merged upstream** (spaceqat/fatqat#52: process shot workers sized by the CPU affinity mask), which makes me a contributor to upstream FatQat.

## Result

<a href={siteUrl("/demos/#fatqat-bench")}>Explore the recorded timings in the Lab</a>: change the requested output, state size and product mode, then inspect the source run behind each CPU/GPU comparison.

**Speed, on the archived timing workloads.** Warm complex128 observable calls on 24–28 qubits ran 17–21× faster than the project's own optimized 32-thread CPU engine with default error-compensated GPU products and simplification off (6–7× with the full state copied back). Synchronisation and requested host output are included; imports, construction and first-call compilation are excluded. Optional plain mode reached 23–26×. The r9 engines recorded 35–42×, before compensated products became the default and the CPU engine got faster.

**Accuracy, on a separate small-circuit study.** On 110 small circuits, up to 5 qubit/qutrit subsystems, the default mode's maximum component error was within 2.9 machine epsilons of a 60-digit oracle evolving stored complex128 coefficients. That is a measured result for these cases, not an error bound for the larger timing workloads or ideal gates.

**Other archived checks.** Exact shot branching was up to 89× faster than running each shot alone on noiseless circuits with mid-circuit measurements, with identical counts. Randomized differential runs checked results against the reference. On an Apple-silicon Mac, the adaptive CPU-plus-Metal runtime recorded 1.18–1.52× over the CPU reference at 24–26 qubits, with bit-identical output in the measured cases; this is an adaptive-runtime result, not GPU-only acceleration.

## Limits

- The 17–21× figure measures warm complex128 observable calls on 24–28 qubits against a fixed 32-thread CPU baseline; copying the full state back cuts it to 6–7×. It is not whole-program acceleration or a fresh benchmark of today's version.
- The precision experiment uses small circuits and the stored coefficients as its oracle input. It does not measure the numerical error of the larger speed-test workloads.
- The branching speed-up applies to noiseless circuits with mid-circuit measurements; noisy circuits gain far less.
