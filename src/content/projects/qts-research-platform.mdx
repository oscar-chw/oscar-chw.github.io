## The problem

The research team needed tick-level Chinese A-share and crypto data that they could trust and reproduce later on exactly the same rows. The data arrived as compressed vendor archives, each with its own quirks, and no one on the team was building the infrastructure full time. As the only developer, I owned the whole stack.

## What I built

- **A layered store.** Raw deliveries are kept byte-identical. A typed, <Term t="versioned Parquet">versioned Parquet layer</Term> sits above them, and a cleansed layer above that flags bad rows instead of dropping them.
- **A query service for researchers** in Python over HTTP and SQL. It returns Apache Arrow, pins every read to a data version, and <Term t="look-ahead bias">refuses requests that would see the future</Term>.
- **Data cleaning, led with the team:** exact duplicates removed, look-ahead leaks blocked before they reach research data.
- **Shared research infrastructure:** access controls in C, monitoring, transition-based alerting and operator documentation.
- **A market-data relay in Go** that validates requests, terminates TLS and scrubs addresses for HTTP and WebSocket traffic. It replaced a Python prototype; the recorded acceptance walkthrough checked collector connections and remote-login continuity.
- **Guarded AI coding agents:** recoverable deletion and approvals, checked against independently identified bypass cases. Those cases do not establish complete security coverage.

## Result

- **700B+ stored rows in the 2026-10-05 snapshot:** A-share ticks plus crypto market data. The platform also supports Polymarket, which is outside this sum.
- **A separate 420,000-row concurrency fixture:** 12 readers and 5 writers (4 appending, 1 rewriting a partition) kept all 23 of 23 commits; 1,111 version-pinned reads returned without mismatch.
- **500M+ exact A-share duplicates removed**, recorded in the same snapshot, from the cleaning work I led with the team.

Three decisions shaped it:

- **Flag, never drop.** Only exact duplicates are deleted. A cleansing rule that silently removes rows is a rule nobody can audit.
- **Three layers, not two.** When a cleansing rule changes, it reruns from the typed layer instead of re-decoding archives, and every rule's effect stays visible.
- **Safety over peak speed.** The query interface is deliberately slower than hand-written DuckDB SQL. In exchange it gives pinned versions, explicit errors and no look-ahead. Raw DuckDB is still there for those who want it.

## Limits

- The platform's code and data are closed, so the figures above cannot be reproduced from a public repository. The write-up explains the design, and the demo shows the same guarantees on synthetic data.
- The write-up reports no uptime or researcher-usage figures.
- The snapshot counts stored rows, not unique observations. The concurrency fixture is a correctness check on a small dataset.
- The first query on a new version rebuilds its file list and was not timed. No cold-query latency bound is claimed here.
