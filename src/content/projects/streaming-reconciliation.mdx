## The problem

At the Hong Kong Universities Web3 Quant Trading Hackathon, where I initiated the project and was lead architect, our trading system recorded each closed trade twice, as JSONL and as CSV. Crash retries could add further copies. Profit and loss is only right if every close is counted exactly once, and the original reader did that by holding every row in memory, so its memory grew with the trading history.

## What I built

- **A retry-safe writer** that tags every close with a caller-supplied identity.
- **A streaming reader** that hashes the bytes it reads and <Term t="external sort">spills size-capped sorted runs to disk</Term>. A heap merge then counts each identity once, using exact decimals.
- **Refusal over guessing.** Conflicting copies of the same close stop the run instead of being silently resolved.
- **The old in-memory reader is kept** as the measured control.

## Result

On a 225k-row synthetic benchmark, peak memory fell 96% (684 MB to under 30 MB) in 12% less time than the in-memory reader. The output was identical, and the reader recovered correctly when killed midway. The [demo](../../demos/reconciliation/) animates both readers on the measured runs.

- **Duplicates are decided by identity, never by value**, so two genuinely identical trades both survive.
- **An external sort replaced an earlier SQLite index**, which used less memory than the original reader but was slower and failed the resource gate.

## Limits

- The evidence is synthetic, measured on one Python version.
- The time win depends on scale: at small inputs, the streaming reader is not faster.
- The writer rewrites the whole day on each append, and there is no multi-host coordination (POSIX only).
